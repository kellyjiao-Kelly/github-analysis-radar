# Github分析雷达

当前文档版本：`v1.1.0`

一个面向非技术用户的 GitHub 项目分析与 AI 编程工程设计陪练 Skill（可以理解成：交给 Codex 的一套固定工作方法）。

它解决的是：面对一个陌生项目时，普通人容易被 README（项目说明）、目录和技术名词淹没，即使看完也不知道项目是否适合自己、应该怎么用，更难从中训练系统拆分、数据设计和长期演进的判断能力。

Github分析雷达会先用大白话说明项目解决的现实问题，再用当前文档、配置、少量关键源码和测试核对结论，最后给出可执行的使用路线。用户明确要求时，还可以把真实项目变成一次工程设计或架构思考陪练。

## Skill 亮点

### 1. 第一屏先讲“它解决什么问题”

不从技术名词和文件目录讲起，先说明谁在什么场景下遇到了什么麻烦，这个项目把哪件事变得更容易。

### 2. 重要结论都有证据边界

把结论分成：

- 已确认：有当前版本的文档、配置、源码或测试支持；
- 合理推断：根据现有材料推测，但没有直接说明；
- 暂未确认：材料不足或不同来源存在冲突。

### 3. 不只告诉你“是什么”，还回答“怎么真正用上”

一次完整分析必须给出：

- 使用结论：直接使用、配置后使用、只复用部分、只学习思路或不建议使用；
- 最快体验；
- 接入现有流程的位置；
- 最小复用内容；
- 最小验证方法；
- 不建议做什么。

### 4. 默认快速分析，需要时才深入

第一次先建立认知地图，不把整个仓库一次塞给用户。继续深入时，每轮只研究一个关键问题，并用源码和测试复核上一轮结论。

### 5. 用真实项目训练工程设计

工程设计陪练不是背架构术语，而是围绕一个真实决定训练：

```text
限制与证据 → 可选方案 → 当前收益与未来代价 → 当前选择
→ 重新评估信号 → 最小验证 → 回退与复盘
```

它会帮助用户判断：

- 功能应该留在现有程序，还是单独划分；
- 数据应该放在本地文件、数据库还是云端；
- 不同部分应该直接调用，还是建立稳定的传话入口；
- 哪些地方现在保持简单，哪些地方需要预留边界；
- 什么情况下才值得拆成独立服务；
- 怎样隔离故障并支持长期演进。

### 6. 架构思考不等于把系统做复杂

默认先判断同一个程序内部划清职责是否足够。只有真实出现独立失败、独立部署、独立扩容或独立权限等需求时，才考虑更重的拆分方式。

### 7. 默认只读，保护电脑和项目

未经用户明确授权，不安装依赖（项目运行需要的工具包）、不运行陌生代码、不修改源码、不部署、不提交代码，也不读取或展示密钥。

## 四种使用方式

| 使用方式 | 适合什么时候 | Skill 会怎么做 |
|---|---|---|
| 快速分析 | 第一次认识项目 | 说明问题、流程、核心部分、使用结论和阅读入口 |
| 单点深入 | 想看懂一个关键设计 | 每轮只追踪一个问题，用源码和测试复核 |
| 工程设计评审 | 已经有自己的方案，希望判断是否合理 | 先给结论，再比较限制、方案、代价、升级信号和回退 |
| 工程设计陪练 | 希望训练自己的判断能力 | 先让用户选择和说明理由，再反馈遗漏、取舍和迁移方法 |

## 安装方法

在 Mac 的“终端”中运行：

```bash
git clone https://github.com/kellyjiao-Kelly/github-analysis-radar.git ~/.codex/skills/github-analysis-radar
```

安装后，新建一个 Codex 任务，让 Codex 重新读取本地 Skill。

如果之前就是通过 `git clone`（克隆 GitHub 仓库）安装的，可以更新：

```bash
cd ~/.codex/skills/github-analysis-radar
git pull
```

如果该目录不是 Git 仓库，不要直接执行 `git pull`；请先备份自己的修改，再重新下载或手动覆盖 Skill 文件。

## 使用方法

### 1. 快速分析一个 GitHub 项目

```text
使用 $github-analysis-radar 分析这个项目：
https://github.com/owner/repository

告诉我它解决什么问题、怎么工作、我怎么真正用上，
并给出最小验证和不建议做什么。
```

### 2. 分析本地项目

```text
使用 $github-analysis-radar 分析这个本地项目：
/你的项目绝对路径
```

### 3. 继续深入一个问题

```text
继续深入，本轮只研究：
这个项目的核心数据是怎样流转的？请用源码和测试验证。
```

### 4. 直接评审工程设计

```text
使用 $github-analysis-radar 帮我判断这个工程设计：

当前项目：一个每周自动生成并发送报告的 Python 工具。
已经确定：未来增加飞书发送。
暂不确定：以后是否增加邮件。

我现在应该把发送功能拆成独立服务吗？请直接给建议，
并说明当前选择、以后升级的信号、最小验证和回退方法。
```

### 5. 开始工程设计陪练

```text
使用 $github-analysis-radar 分析这个项目，并带我完成一次工程设计陪练：
https://github.com/owner/repository

本轮只选择一个关键架构决定。先让我自己判断，
不要提前公布项目采用的真实答案。
```

## 工程设计陪练怎样进行

每轮默认只处理一个决定：

1. 确认当前问题和关键限制；
2. 区分已确认事实、合理假设和暂未确认；
3. 给出最多三个可行方案；
4. 陪练方式先让用户选择并说明理由；
5. 对比当前收益、未来修改代价和回退难度；
6. 分清现在保持简单、现在预留边界、出现信号后再做；
7. 形成工程决策卡；
8. 后续用真实结果复盘。

成长过程不用没有依据的百分制评分，而是观察四个阶段：

- 看得见：能发现设计选择；
- 说得清：能说明限制和不同方案的取舍；
- 做得出：能给出当前决定、理由和重新评估条件；
- 复盘得了：能根据真实结果修正原来的决定。

## 输出内容

普通快速分析通常包括：

1. 它解决什么问题；
2. 它怎么解决；
3. 最值得认识的核心部分；
4. 最值得学习的设计；
5. 怎么真正用上；
6. 推荐先读哪些文件；
7. 证据位置和暂未确认的边界。

工程设计陪练通常增加：

1. 本轮设计决定；
2. 已确认事实、假设和未知；
3. 方案与取舍；
4. 当前选择和时间分层；
5. 架构思考；
6. 验证、回退和重新评估信号；
7. 本轮成长反馈。

## 使用边界

这个 Skill 用于帮助用户理解项目、评审设计和训练判断，不代表被分析项目已经安全、可运行或适合商用。

需要特别注意：

- “值得学习”不等于可以直接复制代码；
- “架构更复杂”不等于工程质量更高；
- “拆成独立服务”不等于自动获得安全隔离；
- 没有实际运行时，不承诺项目开箱即用；
- 安装依赖、执行陌生代码、配置密钥或投入正式业务前，先做可回退的小范围验证。
